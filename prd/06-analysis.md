# 06. 分析機能

本プロジェクトの動機は「どのアップグレードをどのタイミングで取ったか」「ハイスコアの傾向」を見ることである。
ただし**統計的（推論的）分析は Phase2**とし、MVP はまず**記述的分析**で「確実に取り込め、閲覧でき、傾向を眺められる」状態を作る。

データ構造は [03](./03-data-model.md)、用語は [01](./01-game-domain.md) を参照。

---

## 1. MVP（記述的）

### 1.1 基盤

- **run 一覧**: フィルタ/ソート（`played_at`・`final_score` 等）。
- **run 詳細**: コア指標 / アップグレード履歴（週・順序・reroll を可視化）/ リワード台帳 / 添付スクショの閲覧・編集・削除。
- **自己ベスト・自分の run 内ランキング**: `final_score` 等の上位。

#### 精度の方針: 全データを乗せ、後から直す

**分析に 100% の精度を求めない。** スコアはゲームのランダム性・プレイヤースキル・その日の調子といった
**分析対象外の要因で大きく変動する**。語句の読み違いが1つ混ざって系統構成のバーが1本ぶんズレることの影響は、
その分散に埋もれる。

したがって、**集計対象を「正しいと確認できたもの」に絞らない**。

- **未検証（`unverified`）の語句も集計に乗せる。** 除外しない。
- **未分類（`unknown`）の系統も集計に乗せる。** 「未分類」を一級のバケットとして表示する。
- 曖昧さは**語句単位の「未検証」バッジで明示する**にとどめる（分析結果に多少の揺れがありうる、という通知）。
- 語句や系統は**後から直る前提**で扱う。現状の集計はキャッシュせず毎回 SQL で組み立てるため（§4）、
  **直せば次の描画から反映される**。分析結果が後から少し変わることを許容する。

**目指すのは「時間とともに信頼性が上がるシステム」である。** ゲームのアップデート直後は知らない contract が
混ざっていてよい。投入が進み、スクショが集まり、語句が verify され、系統が分類されるにつれて、
**同じデータの分析結果が静かに正確になっていく**。この単調改善を止めないことが設計の要点であり、
逆に「正しいと確認できるまで集計に入れない」設計は、精度を上げるどころか**アップデート直後に分析を空にする**。

→ この方針の帰結として、`verified` は**表示専用の属性**であり、投入・確定・分析・サジェストを分岐させない
（[08](./08-catalog-lifecycle.md) §9.1）。

### 1.2 記述的分析ビュー

- **スコア散布図**: `final_score` × `played_at` の**散布図**（ゲームにランダム性があり、
  run は 1日1回でもないため折れ線にしない）。横軸は**実時間 ⇄ 順番（run を等間隔に詰める）**を
  切替可能（日が空いた際の不自然な横伸び対策。タイムラインと共通トグル）。
- **アップグレード取得タイムライン**（対象は直近 N run。上限は UI に明示。2モード）:
  - **系統構成（既定）**: run ごとのカードに**週×系統の取得数を積み上げ棒**で表示。
    並び順は**時系列 ⇄ スコア順**を切替（「どの要素がスコアを伸ばすか」の目視分析には
    日付軸は不要 — スコア順に並べて構成の勾配を読む）。カードは**縦1列**（読み順を一意にする）、
    左端アクセントは**スコア低→高＝暗→明の indigo 単一 hue ランプ**（散布図のスコア点と同系統。
    validator 検証済み）。週軸は W1〜全 run の最大週にゼロ埋め、Y 上限も全カード共通
    （カード間で取得タイミング・積み上げ高さを比較可能にするため）。
    分類は二次情報由来の暫定マッピング
    （`shared/src/series.ts`、[01](./01-game-domain.md) §3）。カタログ属性への昇格は Phase2 で判断。
  - **アップグレード別**: y=カタログ名（取得頻度降順）× x=run のドットマトリクス。
    **色 = 系統**（主砲=緑 / 核=黄 / シールド=青 / フレイル=紫 / 自動防衛=赤 /
    OU・未分類=保留につき無彩色。配色は validator 検証済み）。週はツールチップ。
- ~~アップグレード頻度~~・~~取得タイミング分布~~: **削除済み**（取得タイムラインが役割を兼ねるため。
  頻度はほぼ全て1回でランキングの意味が薄かった）。
- 上部の集計値は**確定ラン数・ベストスコア**のみ（平均スコアは下手な時期も均されて意味が薄いため出さない）。

### 1.3 最小カタログ管理（記述分析の前提条件）

- 名寄せが崩れると頻度・タイミング分布が壊れるため、MVP に**最小限**のカタログ管理を含める。
- 操作は3つ:
  - **未検証（unverified）一覧**の表示。
  - 既存エントリへの**エイリアス統合（マージ）**（[03](./03-data-model.md) §3.6）。
  - **孤児削除**（参照ゼロの誤読残骸。[08](./08-catalog-lifecycle.md) §7）。
- **verify は UI から行わない。** 昇格は `prd/samples/` への画像コミット＋seed の `evidence` 記述で、必ず PR を通す
  （[08](./08-catalog-lifecycle.md) §5・§6。カタログ管理の正典は 08）。UI はその PR を書くための
  seed スニペットを出すところまで。
- リッチ属性（カテゴリ・色・レアリティ）は Phase2。

## 2. Phase2（推論的・本命）: 傾向分析

**目的**: 「どの系統の contract を、いつ取るとスコアが伸びるか」の傾向を出す。
`/analysis` の**タブ**として、§1 の記述分析と並べる。

### 2.1 生存日数は交絡因子ではなく媒介因子である（設計の中心）

素朴な集計は、ほぼすべて「どこまで生き延びたか」を測ってしまう。本番 18 run の実測:

| 相関（対 `final_score`） | |
|---|---|
| 取得数 | spearman **0.998** |
| `aliens_defeated` | pearson 0.997 |
| `days_survived` | pearson 0.943 |

到達週でスコアが**完全に階層化**しており（W1: 51-63k / W2: 130-143k / W3: 244-412k / W4: 537-623k、
重なりゼロ）、「X を取った run はスコアが高い」は「X が出る頃まで生き延びた」の言い換えになる。

しかし**生存日数は交絡因子ではない**。因果構造はこうなっている。

```
系統構成（ビルド）─┬─→ 生存日数 ─→ スコア
                   └──────────────→ スコア（同じ日数でも稼ぎが違う）
```

生存日数は**媒介因子**であり、調整するとビルドの効果のうち「生存を伸ばした分」が消える。
「スコアを最大化したい」が目的なら、それは**測りたい効果そのもの**である。

→ **原則: アウトカムは割らない。説明変数は率にする。**

| 量 | 役割 | 日数で割るか |
|---|---|---|
| `final_score` | アウトカム | **✗**（`score/day` は過剰調整。実測でも `days` との相関が 0.943 → 0.407 に落ち、生存の情報をほぼ捨てる） |
| `nukes_launched` | 行動指標 | **✓**（「長く生きたから多く撃った」を除くのは正しい） |
| `reroll_count` | 行動指標 | **✓**（機会あたりの率。生の回数は r=0.530 だが、率にすると r=0.074 まで落ちる＝相関は丸ごと生存交絡だった） |

同じ理由で、**系統は「シェア（構成比）」でなく「取得数」で見る**。シェアは分母が run 長に依存し、
系統ごとに意味が変わる（`nuke` は run 長に関わらず 3〜6 個で打ち止めなので、シェアは実質「生存の逆数」になる）。

### 2.2 アウトカムは2つ並べる

`days_survived`（直接観測・分散が小さい）と `final_score`（目的関数）の**両方**を出す。
どちらが先かはデータからは決められないので、**押し付けずに並べる**。
「長生き型ビルド」と「短期稼ぎ型ビルド」は別の戦略であり得る。

**二重軸にはしない**（尺度が 5〜28 と 51k〜623k で桁が違う）。左右2列のパネルに分ける。

### 2.3 説明変数

| 対象 | 説明変数 |
|---|---|
| 系統（11種） | **取得数** と **初出の仮取得日**（[01](./01-game-domain.md) §2.1）。上部でトグル |
| OU（個別） | **取得の有無** と **取得の仮取得日** |
| run 単位 | **リロール率**（回/取得機会）、**核発射/日** |

**系統は 11 種**とする。主砲の4経路（`volley` / `coil` / `basilisk` / `blunderbuss`）と
「主砲共通」を、核・シールド・フレイル・自動防衛と**同格に横並び**にする（[01](./01-game-domain.md) §3）。
経路選択はプレイヤー最大の意思決定であり、`railgun` に畳むとそれが見えなくなる。

分岐前の共通強化は「主砲共通」に入れ、**`upgradeSeriesOf(name)` は名前だけから系統を返す純粋関数のまま保つ**
（run ごとに割り当てを変えない。`shared` の単一真実を壊さないため）。

### 2.4 可視化

- **系統ごとの小さな散布図（small multiples）**。1行 = 1系統、左が `× 生存日数`、右が `× スコア`。
  x 軸（取得数 / 初出仮取得日）は上部でトグル。**平均バーにしない** — SD が平均の 67% あり、
  平均だけを出すと分散に埋もれた差を実在するかのように見せてしまう。
- **点 = run。色はスコアの indigo ランプ**（§1.2 のタイムラインと共用）。
  `× 生存日数` のパネルだけでスコアの強弱も読めるので、「長生きしたが稼げていない run」が見つかる。
- **その系統を取らなかった run は左端の「未取得」列**に置く（OU パネル・初出日パネル共通）。
  比較対象が見えないと「取るべきか」の判断材料にならない。
- **既存の積み上げ棒・ドットマトリクスは 7 系統のまま**。図の仕事が違えば粒度が違ってよい
  （あちらは run の構成を俯瞰するのが仕事）。11 色は知覚上の限界を超えるため、
  新パネルは**ラベルで識別し、主砲5種は同じ緑**にする。

### 2.5 n 不足の扱い

**`n < 5` に「データ不足」バッジを付ける。ただし集計からは除外しない。**
§1.1 の「未検証バッジで明示するにとどめる」と同じ扱いで、**表示専用の属性**とする
（[08](./08-catalog-lifecycle.md) §9.1 の「機能の前提条件にしない」と同じ思想）。
n が増えればバッジは黙って消える。

### 2.6 進め方

**まずシンプルな集計で現象を見る → その後、懸念される効果を取り除いてもう一度見る。**
現象が分かる前に補正を入れると、何が起きていたのか分からなくなる。

**観測データから閾値を作らない。** 「OU は取得順 #15 以降にしか出ない」は 24 件の観測が
たまたまそうだっただけで、ゲームのルールではなかった。偶然の境界を制度として固定しない。

### 2.7 今回のスコープ外

- **個別 contract の分析** — 62 種中 17 種が n=1。加えて経路排他と前提チェーンで交絡が分離できない。
  系統粒度が先。
- **提示された選択肢の記録** — 「X を取らなかった run」は「提示されたが選ばなかった」と
  「そもそも提示されなかった」の混合である。提示は `SIGN CONTRACTS` 画面の左パネルに写るが、
  記録には run あたり週数ぶんの撮影が要り、結果画面 3 枚とはコストの桁が違う。**当面やらない**。
- **contract tree のノード数による「取り切り度」** — ブランチの大きさが違うため系統間で取得数を
  横並び比較できない（`automation` 13 個と `nuke` 5 個は偏重ではない）。ツリーの証拠シートが
  貯まれば正規化できる（[08](./08-catalog-lifecycle.md) §3.1）。
- **リワード分析**: どの reward が点・頻度に効くか。
- カタログのリッチ属性（カテゴリ別の傾向など）。

## 3. Phase3（横断・要オプトイン）

- 匿名の**全体統計**、検討中の**横断ランキング**（[05](./05-auth-and-privacy.md) §4）。
- 自己申告スコアの信頼性対策が前提。

## 4. 実装メモ

- 集計は素のクエリで（事前集計テーブルは作らない。[03](./03-data-model.md) §6）。実測で遅ければ導入を検討する。
- グラフ描画ライブラリは実装時に選定（軽量な可視化で十分）。

### 4.1 将来キャッシュ／事前集計を入れるときの条件

分析が重くなればキャッシュや事前集計を入れてよい。ただし §1.1 の「**時間とともに信頼性が上がる**」を
壊してはならない。具体的には、**語句のマージ・訂正・系統分類の追加が、いずれ分析結果へ反映されること**を
保証する経路が要る。満たし方は問わない（実装時に選ぶ）:

- 訂正イベントで**該当キャッシュを無効化**する、または
- 古いデータは更新せず、**パフォーマンスに影響しない範囲で漸進的に再集計**する（遅れて正確になるのは許容。
  §1.1 の思想と整合する）。

**やってはいけないのは、訂正が永久に反映されない集計を作ること**（＝誤読が凍結される）。
